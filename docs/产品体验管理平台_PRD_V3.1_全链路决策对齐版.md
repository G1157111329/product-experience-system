## 0.1 V3.1 修订摘要与决策对齐

V3.1 不推翻 V3.0 的“体验任务 -> 事实记录 -> 问题闭环 -> 报告交付”主线，而是将其升级为可安全实施、可迁移、可演进的完整设计。V3.1 的目标是解决两类缺口：

1. **工程治理缺口**：补齐数据契约、迁移回填、基础导出作业、AI 字段兼容、字典服务端化、Wave 门禁与回滚策略。
2. **呈现能力缺口**：保留 V2.6 的就地证据位、指标公式面板、可比性声明、矩阵固定上下文、报告快照与发布规则；但不恢复用户创建时模板选择、五种独立 View Mode 或右侧抽屉。

V3.1.1 评审补丁（§27）针对评审发现的歧义、缺项与历史反馈最高准则冲突，给出权威增量：AI Provider 政策（Bear-Model-VL 默认）、报告前台不出现"AI"字样、矩阵单元格录入三槽位、五感/操作融入问题分类、报告—问题深链协议、阶段聚合可执行规则、录入态与报告呈现交互规范（独立章节）、等保三级准备度矩阵。本节为权威增量，与主文不一致时以 §27 为准。

V3.1 保持以下已确认 UX 原则：

- 不在新建任务时要求用户选择报告模板。
- 不将数据与证据拆成独立阅读模式；它们必须贴近问题、结果、指标或复测结论。
- 不使用右侧详情抽屉作为核心交互；采用行内展开、全屏媒体预览、独立详情页或独立指标明细页。
- 顶部不重复写结论；全报告只有一个可确认的“报告总结”。
- 食谱/功能卡默认展示食谱、食材/前置条件、功能效果、关键证据和关联问题；步骤默认折叠，异常步骤优先显露。

## 0.2 产品边界

本平台服务于产品体验测试、试制/试产体验、竞品对比、功能/食谱效果验证、问题整改与复测、体验报告交付。

平台不承担以下职责：

- 不替代上游的需求立项、样机申请、项目排期或 PLM/BOM 主数据系统。
- 不替代研发缺陷管理系统；可与其建立问题链接或同步，但体验问题闭环以本平台为准。
- 不提供自由画布式文档排版。
- 不将任意 Excel 无损还原为网页；Excel 先作为来源附件，结构化导入仅支持明确配置的模板。
- 不允许未确认的 AI 结论作为正式发布结论。
- 不以“评分排名”替代可比性判断；弱可比和不可比数据不得输出默认最优推荐。

# 1. 背景、问题与设计原则

## 1.1 当前业务问题

现有体验报告以 Excel 为主要载体。Excel 在“行列关系、就近图片、临时编辑、公式查看”方面高效，但在以下方面存在长期问题：

| 问题 | 业务影响 | 平台应对 |
|---|---|---|
| 任务入口分散 | 需求、样机、测试对象、责任人需要重复填报 | 统一体验任务，未来接收外部系统申请事件 |
| 过程记录与报告混写 | 记录人一边做测试一边维护长报告，打断体验过程 | 先记录业务事实，再自动组织为报告 |
| 问题难跨报告追踪 | 同一问题在试制、试产、复测中被重复新建 | 建立问题主档与问题出现记录 |
| 图片和指标缺少稳定语义 | 图片贴在单元格旁，但系统无法理解其对应对象 | 证据按业务对象绑定，保留来源、时间、上传人 |
| 对比关系不稳定 | 多对象、食材、阶段、指标混在同一表，阅读成本高 | 根据内容推断适宜的展示方式，但不改变底层数据 |
| 整改闭环靠人工催办 | 责任、计划、复测、关闭缺少状态与提醒 | 明确整改与复测状态机、提醒与升级 |
| 报告阅读路径单一 | 工程师、产品、管理层在同一长页面中寻找各自信息 | 全量报告、汇报简报、问题详情三种路径共享同一数据 |
| 导入与系统衔接不稳定 | Excel 和上游需求表单难直接复用 | 先保留附件与来源标识，未来按契约接入 |

## 1.2 三类样本对平台的启示

三类已提供样本显示，报告在业务上天然有不同重心：

| 样本形态 | 主要阅读任务 | 平台默认渲染策略 | 用户不需要做的选择 |
|---|---|---|---|
| 多台和面机同条件对比 | 看同一食谱/项目下对象差异、关键问题与证据 | 对比矩阵或混合对比 | 不需在新建时选择“矩阵模板” |
| 原汁机不同口径/食材效果 | 看食材 x 口径 x 指标与异常原因 | 指标强化表 + 异常证据 | 不需在新建时选择“指标报告” |
| 同型号跨研究/试制/试产 | 看问题是否复现、整改是否有效、风险如何演进 | 阶段演进与问题轨迹 | 不需在新建时选择“阶段报告” |

## 1.3 产品原则

1. **任务先于报告**：用户承接的是体验任务；报告是任务中结构化事实的呈现与交付。
2. **问题优先**：问题是产品决策、研发整改和风险管理的共同语言。
3. **证据随对象**：图片、视频、原始指标不进入独立“素材区”后再人工寻找，而是随问题、功能效果、指标异常或复测结果出现。
4. **一份报告只有一个报告总结**：标题区不重复生成结论文字；顶部只展示元信息、状态和数量。
5. **录入不要求预判报告形态**：用户先录入事实；平台在阅读/导出时使用渲染策略生成更适合的版面。
6. **渐进披露，不打断阅读**：简要内容默认可扫读；步骤、原始数据、全部证据在当前上下文就地展开或进入独立详情页。
7. **人始终确认关键判断**：AI 可辅助归纳、推荐关联、发现缺失，但不能越过人工确认、可比性校验和发布规则。
8. **所有自动化都可追溯**：自动建任务、自动分配、自动计算、自动提醒、AI 建议均需保留来源、规则版本、执行结果与人工修正记录。
9. **预留完整、实现分期**：`RESERVED` 能力必须有对象、契约、状态、异常和权限设计，但当前代码、接口开关、页面入口不提前上线。

# 2. 目标、非目标与成功指标

## 2.1 产品目标

| 编号 | 目标 |
|---|---|
| G-01 | 体验人员可在最少重复填写下完成任务承接、功能记录、问题创建、证据上传和提交审核。 |
| G-02 | 产品、研发、设计可在报告中优先看到问题、影响、证据、整改和复测状态。 |
| G-03 | 报告比 Excel 更容易阅读，但保留 Excel 的结构优势：稳定关系、指标公式、就近证据、分组与冻结上下文。 |
| G-04 | 同一问题可跨报告追踪其发现、整改、复测与关闭历程。 |
| G-05 | 后续接入外部需求系统时，可安全、幂等地自动创建任务、预填字段并进行规则分配。 |
| G-06 | 报告、问题、证据、整改、复测、通知与导出均可审计、可定位、可追溯。 |

## 2.2 交付分层与成功判定

| 层级 | 定位 | 核心结果 | 成功判定 |
|---|---|---|---|
| Wave 0 / P0 技术地基 | 先解决契约、迁移、权限、字典、导出可靠性 | 新旧数据安全共存；关键异步作业可观测、可恢复 | 迁移演练通过；导出失败可重试；权限、状态和字典接口完成合约测试 |
| Wave 1 / P0 业务闭环 | 打通从手动任务到报告发布与问题复测 | 任务、记录、证据、问题、整改、复测、报告、通知可在真实样本中闭环 | 三类样本均完成端到端验收；高等级问题与复测阻断生效 |
| Wave 2 / P1 报告资产增强 | 提升管理层阅读、历史追溯与受控迁移能力 | 汇报简报、问题轨迹、报告运营概览、受控 Excel 导入试点 | 简报由同一快照生成；受控模板导入只能生成待确认草稿 |
| RESERVED | 明确未来边界，不进入当前排期或代码入口 | 外部接入、自动分配、复杂 PDF、通用导入、相似问题推荐 | 满足实施前检查清单后方可立项 |

## 2.3 非目标与明确不回退项

- 不把 V2.6 的五种 View Mode 恢复为前台常驻模式。
- 不把数据、证据拆成独立页面后要求用户反复切换；研发深度分析通过当前模块的“指标明细页/原始数据展开”完成。
- 不在 P0 中开放用户可见的报告模板选择器。
- 不在 P0 中做任意 Excel 的无损解析、复杂合并单元格/图片语义识别或自动发布。
- 不在 P0 中做外部系统实时双向同步、自动规则分配或 AI 自动创建/关闭问题。
- 不在 P0 中实现复杂 A3 分册、分页预检和多 Profile 打印；但必须实现基础导出作业可靠性。
- 不在 P0 中以“评分排名”替代可比性判断；弱可比与不可比不输出默认最优推荐。
- 不使用右侧详情抽屉作为报告、问题或矩阵的主阅读/编辑入口。

# 3. 核心概念、对象与关系

## 3.1 统一对象定义

| 对象 | 定义 | 关键责任 |
|---|---|---|
| 体验任务 `Task` | 某一产品/样机/阶段/对象范围内的体验工作单元 | 承接、分配、执行、提交、归档 |
| 测试对象 `TestObject` | 被体验或被对比的实体，如本机、竞品、变体、历史阶段样机 | 提供对象上下文与可比性基础 |
| 记录项 `RecordItem` | 对某项功能、食谱、场景、五感、步骤或指标的事实记录 | 承载结果、说明、指标、关联问题与证据 |
| 指标记录 `MetricRecord` | 原始值、计算值、阈值与结论 | 支持公式、版本、异常解释 |
| 证据 `Evidence` | 图片、视频、附件、现场记录等 | 可关联多个业务对象，保留原始来源 |
| 问题主档 `Issue` | 可跨报告持续追踪的产品问题实体 | 负责状态、责任、整改、复测与关闭 |
| 问题出现记录 `IssueOccurrence` | 某问题在某个任务/报告/记录项中的一次发现或复现 | 保存当次现象、证据、影响与上下文 |
| 整改动作 `RectificationAction` | 针对问题制定并执行的整改计划 | 记录负责人、期限、方案、结果 |
| 复测 `Verification` | 对整改后的验证活动 | 确认通过、失败、需补证据或重新打开 |
| 报告 `Report` | 对任务或多个来源任务/报告生成的阅读与交付视图 | 汇总、阅读、发布、导出、分享 |
| 报告总结 `ReportSummary` | 该报告唯一的文字性结论模块 | 人工维护或确认 AI 生成结果 |
| 报告渲染策略 `RenderProfile` | 根据数据结构选择的阅读布局规则 | 后台推断，不作为创建时的用户选择 |
| 通知 `Notification` | 任务、问题、整改、审核、发布等事件的提醒载体 | 站内、邮件/IM 渠道适配、已读与升级 |
| 来源连接 `SourceLink` | 外部申请、原始 Excel、来源报告等的可追溯链接 | 预留外部系统与导入设计 |

## 3.2 关系模型

```text
外部申请 / 手动创建
        ↓
     体验任务 Task
        ├─ 测试对象 TestObject (1..N)
        ├─ 记录项 RecordItem (1..N)
        │     ├─ 指标记录 MetricRecord (0..N)
        │     ├─ 证据 Evidence (0..N)
        │     └─ 问题出现记录 IssueOccurrence (0..N)
        ├─ 报告 Report (0..N)
        └─ 任务附件/来源链接 SourceLink (0..N)

问题主档 Issue
        ├─ 问题出现记录 IssueOccurrence (1..N)
        ├─ 整改动作 RectificationAction (0..N)
        └─ 复测 Verification (0..N)
              └─ 证据 Evidence (0..N)
```

## 3.3 关键建模约束与业务类型边界

1. `Issue` 是主档，`IssueOccurrence` 是某一次观察到的问题事实。两个概念不得混用。
2. `Evidence` 使用多态关联表 `evidence_links`，可同时关联 `RecordItem`、`MetricRecord`、`IssueOccurrence`、`RectificationAction`、`Verification`、`Report`、`ReportSnapshot`。
3. `Report` 不拥有问题真相；报告只引用任务数据和问题出现记录。发布时生成不可变 `ReportSnapshot`。
4. `report_scope_type` 是报告的**业务资产语义**；决定来源、可比性、权限与发布校验。`render_profile` 是**显示策略**；只影响阅读布局，不能替代业务类型。
5. `RenderProfile` 不改变原始任务、记录、问题、指标和证据数据；变更布局不应重写事实数据。
6. 任务和报告的删改不应破坏已发布快照。删除采用软删除或归档，保留审计链。
7. JSONB 仅用于快照、可扩展配置、规则表达式与非查询型结构；任何需要筛选、权限判断、生命周期或审计的核心业务字段必须结构化存储。
8. 自动化产生的字段必须可定位来源：规则版本、输入范围、模型版本、操作者与执行时间。

## 3.4 报告业务类型与渲染策略

### 报告业务类型：决定业务规则

| `report_scope_type` | 来源与规则 | 默认可比性/发布限制 |
|---|---|---|
| `task_report` | 单一任务或同一任务的多个测试对象 | 依任务条件校验 |
| `comparison_report` | 多对象或多型号同一计划内对比 | 必须确认对象、条件、字段对齐与可比性 |
| `model_dossier_report` | 同型号多个阶段/多任务归集 | 不做“最优对象”排名；强调问题/效果演进 |
| `synthesis_report` | 多来源专题总结 | 首页必须说明来源、字段对齐与可比性边界；默认不排名 |

### 渲染策略：决定阅读布局

| `render_profile` | 适用内容 | 不能决定的事项 |
|---|---|---|
| `single_narrative` | 单对象、多功能/食谱 | 报告来源与业务类型 |
| `comparison_matrix` | 多对象、对齐项目 | 可比性是否成立 |
| `metric_emphasis` | 指标密集、公式/阈值重要 | 指标是否有效或可用于排名 |
| `mixed_comparison` | 图片、指标、问题同等重要 | 报告发布权限 |
| `stage_timeline` | 跨阶段、复测/问题演进 | 是否属于型号档案资产 |
| `synthesis` | 多来源专题分析 | 是否允许自动推荐最优对象 |

映射规则：`report_scope_type` 必须先确定；系统根据数据推断推荐 `render_profile`；审核人仅能在允许的候选策略内确认/调整。

# 4. 角色、权限与责任边界

## 4.1 角色定义

| 角色 | 典型人群 | 核心目标 |
|---|---|---|
| 申请人 `requester` | 上游需求发起人/项目成员 | 提交申请、查看关联任务和公开结果 |
| 体验承接人 `experience_executor` | 体验工程师 | 承接任务、记录体验、创建问题、上传证据、提交审核 |
| 任务负责人 `task_owner` | 体验负责人/项目负责人 | 分配、调整范围、退回、关闭/取消任务 |
| 研发整改负责人 `rectification_owner` | 研发、结构、电控、软件等 | 查看问题、提交整改方案、更新计划、发起复测 |
| 设计协作者 `design_collaborator` | 工业设计/交互/包装等 | 补充设计相关分析、查看问题和证据 |
| 产品决策者 `product_manager` | 产品经理/产品工程师 | 阅读报告、确认风险、创建后续验证/任务 |
| 审核发布人 `reviewer` | 体验负责人、指定评审人 | 审核任务/报告、确认结论、发布报告 |
| 管理层读者 `executive_viewer` | 管理人员 | 阅读发布报告与汇报简报，不编辑事实 |
| 平台管理员 `platform_admin` | 系统管理员 | 用户、组织、字典、权限、配置、审计管理 |
| 集成管理员 `integration_admin` | IT/系统集成人员 | 管理外部系统连接、字段映射、分配规则、失败队列 |
| 审计员 `auditor` | 质量/内控 | 只读查看审计与必要的原始记录 |

## 4.2 权限模型

采用 `RBAC + Resource Scope + Attribute Check`：

- RBAC：决定角色可访问的能力。
- Resource Scope：决定用户可访问的组织、产品线、项目、任务。
- Attribute Check：决定是否为任务负责人、问题责任人、审核人、来源系统管理员等。

| 能力 | 允许角色 | 约束 |
|---|---|---|
| 新建手动任务 | executor、task_owner、admin | requester 是否可新建由组织策略决定 |
| 编辑执行中任务 | executor、task_owner、admin | executor 仅限本人承接任务 |
| 创建问题/证据 | executor、task_owner、rectification_owner、reviewer、admin | 后两类只能补充本人有权限范围内的证据 |
| 更新整改 | rectification_owner、task_owner、reviewer、admin | rectification_owner 仅更新本人负责整改；reviewer 以退回/确认方式操作 |
| 发起/填写复测 | executor、task_owner、rectification_owner、reviewer、admin | rectification_owner 可申请；reviewer 可确认结论 |
| 编辑报告总结 | executor、task_owner、reviewer、admin | executor 可草拟；reviewer 负责确认 |
| 发布报告 | reviewer、admin | task_owner 可提交发布申请，不可绕过审核 |
| 查看已发布报告 | 受资源范围控制的全部角色 | executive 只读；分享页额外受分享策略控制 |
| 管理集成/导入 | platform_admin、integration_admin | integration_admin 仅管理连接、映射、异常，不能绕开业务权限 |

## 4.3 权限失败规则

| 场景 | 系统行为 |
|---|---|
| 用户直接访问无权限任务链接 | 返回 403；不泄露标题、人员、产品或问题数量；显示“无访问权限” |
| 用户曾有权限但权限已收回 | 当前页面提示权限已变化，停止自动保存，返回列表页 |
| 用户尝试更新非本人负责的整改 | 返回 403，并展示责任人和可申请协作入口 |
| 发布人尝试发布未审核报告 | 返回 409，展示阻断项与跳转锚点 |
| 外部分享链接过期/撤销 | 返回 410，显示“链接已失效”，不展示缓存内容 |

## 5.4 报告资产入口与阅读路径

报告不是唯一入口，用户可从任务、问题、通知、报告中心和分享链接进入同一份报告。不同入口必须指向同一已授权的报告/快照，且保留返回来源。

| 入口 | 默认定位 | 行为要求 |
|---|---|---|
| 任务详情 | 当前任务生成的报告草稿或已发布版本 | 返回任务时保留记录项焦点与滚动位置 |
| 问题详情 | 包含该问题最近出现记录的报告章节 | 直接定位问题行/问题轨迹，不打开抽屉 |
| 工作台待办 | 审核、补证据、整改、复测或发布阻断点 | URL 必带 `focus`、`source=todo` 与目标对象 ID |
| 报告中心 | 报告全量阅读页 | 默认展示报告总结与问题区 |
| 分享链接 | 已发布快照或汇报简报 | 只读、无内部对象 ID 泄露 |

报告的“全量阅读”和“汇报简报”是同一快照的两条阅读路径；简报每页都可回跳到全量报告对应锚点。

# 6. 关键状态机与统一退回策略

## 6.1 体验任务状态机

```text
draft
  -> pending_assignment
  -> assigned
  -> in_progress
  -> submitted
  -> under_review
  -> completed
  -> archived

pending_assignment -> cancelled
assigned -> pending_assignment        (承接人拒绝/人员变动)
in_progress -> blocked                (缺样机/条件不满足)
blocked -> in_progress
submitted -> in_progress              (审核退回)
under_review -> in_progress           (要求补录)
under_review -> completed
draft/pending_assignment/assigned/in_progress -> cancelled
completed -> reopened                  (发现遗漏或发起补测)
reopened -> in_progress
```

| 状态 | 说明 | 主操作 | 退回原因是否必填 |
|---|---|---|---|
| draft | 尚未提交分配 | 编辑、提交分配、取消 | 否 |
| pending_assignment | 等待指定承接人 | 分配、转待分配池、取消 | 分配失败时必填 |
| assigned | 已分配，待接受/开始 | 接受、拒绝、转交 | 拒绝时必填 |
| in_progress | 正在体验记录 | 保存、创建问题、提交审核、阻塞 | 阻塞时必填 |
| blocked | 因条件无法执行 | 恢复、调整计划、取消 | 是 |
| submitted | 执行人已提交 | 审核、退回 | 退回时必填 |
| under_review | 审核中 | 通过、退回 | 退回时必填 |
| completed | 任务完成 | 查看报告、发起补测/新任务 | 否 |
| reopened | 因新增事项重新打开 | 恢复执行 | 必须关联原因 |
| cancelled | 取消且不可继续 | 查看审计 | 必须记录原因 |

## 6.2 问题状态机

```text
open
 -> triaged
 -> assigned
 -> rectifying
 -> pending_verification
 -> verified_closed

open/triaged/assigned/rectifying/pending_verification -> waived
pending_verification -> rectifying          (复测失败)
verified_closed -> reopened                  (后续复现)
waived -> reopened                           (豁免失效)
```

| 状态 | 责任 | 进入条件 | 可退回/跳转 |
|---|---|---|---|
| open | 创建人/任务负责人 | 已填现象、至少一个上下文；高等级问题需证据或豁免 | 可合并、可分诊 |
| triaged | 任务负责人 | 已确定严重度、所属模块、处理方式 | 退回补充事实 |
| assigned | 整改负责人 | 已分配责任人和计划 | 责任人可拒绝并退回分诊 |
| rectifying | 整改负责人 | 已提交整改方案 | 可更新计划、上传方案证据 |
| pending_verification | 体验/审核方 | 已申请复测 | 复测失败则回到 rectifying |
| verified_closed | 审核人 | 复测通过且有结论/证据 | 后续复现可 reopened |
| waived | 审核人 | 已说明风险接受/不处理原因与有效期 | 到期提醒，必要时 reopened |

## 6.3 报告状态机

```text
draft -> preparing -> pending_review -> changes_requested -> preparing
pending_review -> ready_to_publish -> published -> superseded -> archived
published -> invalidated
```

说明：

- `draft`：任务数据正在汇总，报告可编辑。
- `preparing`：系统重算内容、指标和渲染策略。
- `pending_review`：提交审核。
- `changes_requested`：审核退回，必须含退回说明与定位链接。
- `ready_to_publish`：所有阻断项已通过。
- `published`：创建不可变快照和可分享版本。
- `superseded`：有新发布版本但保留旧版可追溯。
- `invalidated`：发现严重数据错误，保留可审计访问但默认不作为有效交付。

## 6.4 通用退回与失败处理原则

1. 退回不是“状态回滚后消失”：必须记录 `reason_code`、自由文本、操作人、时间、来源对象。
2. 任何异步失败不得悄悄丢失：任务创建、媒体转码、通知、PDF、导入、外部事件均需状态、重试次数和告警。
3. 用户在输入过程中断网或刷新时，草稿应保留；提交失败不清空已输入内容。
4. 状态跃迁由服务端校验，前端只根据服务端返回结果更新。
5. 严重失败可降级：例如 PDF 失败不影响已发布报告阅读；消息渠道失败不影响站内待办生成。


## 6.5 服务端字典、显示状态与状态机边界

字典化解决“名称、排序、启停、展示文案”问题；状态机解决“什么转移是合法的”问题。两者不得混用。

| 对象 | 字典表/接口 | 服务端状态机负责 |
|---|---|---|
| 项目阶段 | `project_phase_dict` | 阶段变更是否允许影响进行中任务 |
| 问题状态显示 | `issue_status_dict` | `open -> triaged -> assigned -> rectifying -> verifying -> closed/reopened/waived` 的合法跃迁 |
| 任务状态显示 | `task_status_dict` | 分配、承接、提交、审核、完成、取消的合法跃迁 |
| 报告状态显示 | `report_status_dict` | 草稿、审核、发布、失效、归档的合法跃迁 |
| 严重度/SLA | `issue_severity_dict`、`sla_policy_dict` | 到期提醒、升级与豁免权限 |
| 产品、组织、指标 | 主数据/定义表 | 外键有效性、版本与启停校验 |

规则：字典字段可由管理员维护展示名、颜色、排序、启用状态；`code` 不可随意改写；状态机 transition 定义存于服务端受版本控制的规则表/代码中，管理员不能通过改字典绕过审批和闭环。

# 7. 模块一：工作台与待办

**实施阶段：P0**

## 7.1 页面目标

用户登录后无需理解复杂体系，应先看到“我要处理什么”。工作台按任务、问题、整改、审核四类待办汇总，不按系统模块堆卡片。

## 7.2 页面结构

```text
顶部：全局搜索 | 新建体验任务 | 通知 | 个人菜单
------------------------------------------------
我的待办
[待承接任务] [执行中任务] [待我整改] [待我审核] [即将到期]
------------------------------------------------
优先处理
- A 级问题复测待确认
- 今日到期整改

------------------------------------------------
最近访问
任务 / 问题 / 报告
```

## 7.3 待办规则

| 待办类型 | 触发事件 | 默认排序 | 点击跳转 |
|---|---|---|---|
| 待承接 | 任务分配给我 | 优先级、计划开始时间 | 任务详情，突出接受/拒绝 |
| 执行中 | 我为执行人且未提交 | 截止时间、最后编辑时间 | 任务工作台 |
| 待我整改 | 我为整改负责人且问题未关闭 | 严重度、计划完成时间 | 问题详情的整改页签 |

| 即将到期 | 任务/整改/复测临近期限 | 距到期时间 | 对应对象 |

## 7.4 失败与边界

- 待办聚合服务异常：显示上次成功更新时间与“刷新重试”，不展示虚假空态。
- 用户无权限的历史待办：自动从列表移除，并记录权限变动审计。
- 同一事项多渠道重复提醒：站内只保留一条聚合待办，渠道发送使用去重键。
- 任务被取消或问题关闭后，未读通知不删除，但点击时提示状态已变化并跳转最新状态。

# 8. 模块二：体验任务创建、分配与承接

## 8.1 创建入口

| 入口 | 阶段 | 说明 |
|---|---|---|
| 手动新建任务 | P0 | 任务负责人/体验人员创建 |
| 从报告/问题发起补测 | P0 | 自动带入产品、对象、问题、复测目标 |
| 从复制历史任务创建 | P1 | 复制结构，不复制问题/结论/证据 |
| 外部系统申请自动创建 | RESERVED | 接收入站事件，映射字段并路由分配 |
| Excel 附件创建草稿 | RESERVED | 上传来源 Excel，先作为附件，不自动解析 |

## 8.2 手动新建任务流程

```text
选择基础信息
 -> 配置测试对象与范围
 -> 选择记录项集合
 -> 指定执行人与计划
 -> 保存草稿 / 提交分配
```

### 8.2.1 基础信息字段

| 字段 | 必填 | 规则 |
|---|---:|---|
| 任务名称 | 是 | 自动建议“产品/型号 + 阶段 + 体验类型”，允许编辑 |
| 产品线/品类/型号 | 是 | 来源于产品字典；支持多个测试对象 |
| 阶段 | 是 | 前期研究/手板/试制/试产/量产/竞品等可配置 |
| 体验目的 | 是 | 200 字内；用于后续报告信息，不等于报告总结 |
| 体验类型 | 是 | 单对象体验、对比体验、复测、专项验证等；只影响默认记录项 |
| 优先级 | 是 | P0/P1/P2 或业务字典；不等同问题严重度 |
| 测试条件摘要 | 否 | 场地、环境、样机状态、原料批次、前置条件 |
| 计划开始/完成时间 | 是 | 结束不得早于开始 |
| 来源链接/附件 | 否 | 可关联上游申请、原始 Excel、邮件/文档 |
| 执行人/承接组 | 是 | 支持先分配到组，再由组内承接 |

### 8.2.2 记录项集合

用户不选择“报告模板”，只选择或继承体验范围：

- 食谱/功能效果。
- 功能/操作步骤。
- 五感/清洁/噪音。
- 指标测量。
- 对比对象。
- 专项检查项。

平台根据 `体验类型 + 产品品类 + 阶段 + 选定范围` 推荐默认记录项；用户可新增、删除、排序。每项有唯一 `record_item_id`，避免后续报表依赖自由文本标题。

## 8.3 分配与承接

### 8.3.1 P0 人工分配

任务负责人选择执行人或承接组，系统校验：

- 执行人具备组织/产品线访问权限。
- 执行人未离职/禁用。
- 截止日期合理。
- 高优任务是否需要至少一名审核人。
- 同一任务不能重复创建相同执行角色。

执行人可“接受”或“拒绝”。拒绝必须选择原因：工作量冲突、能力/权限不匹配、测试条件未具备、其他；拒绝后任务回到 `pending_assignment`，通知任务负责人。

### 8.3.2 RESERVED：外部系统触发与规则分配

#### 设计目标

当上游需求申请通过时，外部系统发送事件。平台按照字段映射和分配规则创建任务、预填基础信息、分配承接组/人，并将结果回写或提供查询状态。

#### 外部事件契约

```json
{
  "event_id": "uuid",
  "event_type": "experience_request.approved",
  "occurred_at": "2026-06-26T10:00:00Z",
  "source_system": "upstream-system",
  "source_record_id": "REQ-20260626-001",
  "schema_version": "1.0",
  "payload": {
    "request_title": "160mm 原汁机试制体验",
    "product_line_code": "JUICER",
    "product_model_code": "YZJ-F01M1",
    "stage_code": "trial",
    "experience_type_code": "comparison",
    "priority_code": "P1",
    "requested_due_at": "2026-07-05T18:00:00+08:00",
    "requester_id": "external-user-id",
    "source_url": "https://source.example/REQ-20260626-001",
    "custom_fields": {}
  }
}
```

#### 字段映射与默认策略

| 外部字段 | 平台字段 | 映射失败策略 |
|---|---|---|
| request_title | task.title | 使用“待补充标题”，进入人工待处理池 |
| product_line_code | task.product_line_id | 无映射：不创建正式任务，进入 `mapping_failed` |
| product_model_code | test_object.model_id | 无映射：创建待确认对象，不允许提交执行 |
| stage_code | task.stage_code | 无映射：使用 `unknown`，要求管理员确认 |
| experience_type_code | task.experience_type | 无映射：使用默认“专项验证”，标记待确认 |
| priority_code | task.priority | 无映射：默认 P2，并记录告警 |
| requested_due_at | task.due_at | 不合法：使用系统默认 SLA，标记待确认 |
| requester_id | source_link.requester_ref | 无匹配：保存原始 ID，不创建内部用户关系 |

#### 分配规则模型

```text
按优先级排序的规则：
产品线 + 品类 + 阶段 + 体验类型 + 地点/组织 + 优先级
  -> 承接组
  -> 可选指定执行人
  -> 审核人
  -> SLA 与提醒策略
```

规则必须具备：

- 生效时间、停用时间、版本号、模拟测试能力。
- 条件冲突检测：多条规则命中时按优先级和最具体匹配原则选择。
- 无规则命中时进入“待分配池”，不得静默分给任意人。
- 人员不可用时优先转承接组，不自动改派到无权限用户。
- 所有自动分配需要写入 `assignment_decision`：命中规则、候选人、最终结果、时间、是否人工改写。

#### 幂等、重试与回退

| 场景 | 行为 |
|---|---|
| 同一 `source_system + event_id` 重复发送 | 返回首次处理结果，不重复建任务 |
| 同一来源单据产生更新事件 | 根据事件类型执行更新；不允许覆盖已执行的关键事实 |
| 签名验证失败 | 拒绝 401/403，记录安全审计，不进入业务队列 |
| 字段映射失败 | 进入集成异常队列，通知集成管理员，不创建半成品正式任务 |
| 分配规则失败 | 可创建 `pending_assignment` 任务，但必须标记“自动分配失败” |
| 消息消费失败 | 指数退避重试；超过阈值进入死信队列；支持人工重放 |
| 回写上游失败 | 平台任务保留；进入回写重试，不回滚已成功建成的任务 |
| 外部撤销申请 | 若任务未开始则取消；若已执行则标记“来源已撤销”，交由任务负责人决定继续/取消 |

**当前实现要求：**仅创建数据模型、接口契约、规则配置原型、权限与测试用例；不接入任何真实系统、不启用事件端点、不部署消费者。

# 9. 模块三：体验任务工作台与录入

**实施阶段：P0**

## 9.1 页面结构

```text
任务信息条：任务名 | 产品/阶段 | 执行状态 | 保存状态 | 提交审核
----------------------------------------------------------------
记录导航：总览 | 功能/食谱 | 指标 | 五感/操作 | 问题 | 附件
----------------------------------------------------------------
当前记录区（按记录项分组）
- 食谱/功能卡
- 指标录入表

- 证据缩略图
- 关联问题
```

任务工作台不是报告预览。它服务于“边体验边记录、少跳转、可恢复”。

## 9.2 统一录入路径

### 9.2.1 食谱/功能效果卡

默认可见字段：

```text
食谱/功能名称
食材清单/前置条件
功能效果（达标/待观察/不达标/不适用）
效果说明
关键证据（0-3）
关联问题（0-N）
[展开步骤与完整过程]
```

“步骤”默认折叠，只在以下情形自动提醒展开：

- 结果为不达标。
- 创建了问题。
- 录入人员主动标记“过程异常”。
- 模板/规则要求某一步必须填写。
- 审核人退回并定位到某步骤。

### 9.2.2 条件触发

| 条件 | 触发 UI | 后台行为 |
|---|---|---|
| 功能效果 = 达标 | 显示简短说明与可选证据 | 可继续下一项 |
| 功能效果 = 待观察 | 显示待补充原因、建议复测时间 | 生成提醒候选，不自动建问题 |
| 功能效果 = 不达标 | 自动打开问题创建区 | 预填当前任务、对象、记录项、步骤、证据 |
| 指标超阈值 | 显示异常说明字段和“创建/关联问题” | 记录规则版本与计算结果 |
| 上传失败 | 当前证据位显示失败状态和重试 | 不丢失文件元数据与本地草稿引用 |
| 同一问题疑似存在 | P1/RESERVED 才可提示候选 | 不自动关联，由用户确认 |

### 9.2.3 问题创建的预填规则

用户从记录项/步骤/指标异常创建问题时，系统自动带入：

- 任务、测试对象、产品型号、阶段。
- 当前记录项、食谱、功能、步骤。
- 当前测试条件与原料/场景。
- 已上传的关键图片/视频/指标记录。
- 建议问题模块/标签（可编辑）。
- 发现人、发现时间。

用户需确认或填写：

- 问题现象。
- 严重度。
- 影响范围。
- 建议方向（可选）。
- 是否关联已有问题主档。
- 责任部门/建议责任人（可选，最终由分诊确认）。

## 9.3 数据录入与证据交互

### 9.3.1 证据上传

支持图片、视频、文档、音频（按组织策略开关）。上传流程：

```text
选择文件 -> 本地校验 -> 分片/直传 -> 病毒扫描 -> 转码/缩略图 -> 可用 -> 绑定业务对象
```

| 阶段 | 规则 |
|---|---|
| 本地校验 | 校验格式、大小、数量、网络状态；不通过即提示 |
| 直传 | 使用短期签名 URL，避免文件经应用服务器中转 |
| 扫描 | 未扫描完成前标记 `processing`，不能作为发布关键证据 |
| 转码 | 视频生成预览图与播放版本；失败时保留原件且允许重试 |
| 绑定 | 必须记录绑定对象、角色（关键/补充/复测前后）、说明 |
| 删除 | 已发布快照引用的证据不能物理删除；仅可标记不可用并说明 |

### 9.3.2 自动保存与冲突

- 字段编辑后 800ms 防抖自动保存；顶部显示“保存中/已保存/保存失败”。
- 提交审核前执行完整校验。
- 使用 `version` 或 `updated_at` 实现乐观锁；冲突时服务端返回 409 和最新版本。
- 冲突页面提供：查看差异、保留我的内容、采用最新内容、复制到备注。不得无提示覆盖。
- 断网时保留本地草稿队列；恢复网络后按顺序同步；发生冲突进入人工处理。

## 9.4 任务提交审核校验

### 阻断项

- 缺少必填测试对象/任务目的/关键记录项结果。
- 不达标记录没有问题或明确豁免说明。
- 高严重度问题没有关键证据或证据豁免原因。
- 指标异常没有异常说明。
- 复测任务没有关联原问题或验证结论。
- 存在未完成上传/扫描失败的关键证据。

### 预警项

- 过程步骤大量为空但未标记不适用。
- 多个问题未分配模块/严重度。
- 任务已超过计划完成时间。
- 存在待观察结果且未规划复测。
- 同一记录项的图片数量超过建议上限。

提交失败时用户停留在当前任务，顶部展示校验摘要，点击后跳转到对应记录项并高亮字段。

## 10.2 问题详情页

```text
问题标题 / 编号 / 严重度 / 状态 / 责任人
------------------------------------------------
概览
- 当前现象、影响、首次发现、最近出现、关联产品
------------------------------------------------

- 每次出现的任务、记录项、证据、原始指标、描述
```

不使用右侧详情抽屉。报告内点击问题进入独立问题详情；仅快速查看场景允许报告行内展开简短信息。

## 10.3 分诊与整改

### 10.3.1 分诊字段

| 字段 | 必填 | 说明 |
|---|---:|---|
| 严重度 | 是 | A/B/C 或组织字典 |
| 问题模块 | 是 | 结构、性能、软件、操作、外观、清洁等 |
| 影响范围 | 是 | 单一食谱/功能、对象、批次、全局等 |
| 处理策略 | 是 | 整改、观察、豁免、合并到既有问题 |
| 整改责任人 | 整改时必填 | 可为部门/用户 |
| 计划完成时间 | 整改时必填 | 用于 SLA |
| 复测要求 | 是 | 是否需复测、建议场景/指标 |
| 分诊说明 | 是 | 解释判断依据 |

### 10.3.2 整改更新

整改负责人可编辑：方案、计划完成时间、执行状态、实际完成时间、整改证据、风险说明。计划延期必须填写原因，触发任务负责人和审核人提醒。

### 10.3.3 复测

复测不在问题页“直接关闭”，而是创建/关联一个复测任务：

```text
问题详情 -> 发起复测
  -> 预填原问题、相关对象、关键场景、验收标准、原始证据链接
  -> 指定复测人/计划
  -> 复测任务完成
  -> 提交复测结论
  -> 审核通过：问题关闭；失败：问题退回整改
```

复测结论：`pass`、`fail`、`partial_pass`、`inconclusive`。

| 结论 | 系统动作 |
|---|---|
| pass | 允许审核关闭问题 |
| fail | 问题转回 `rectifying`，保留失败复测记录 |
| partial_pass | 要求审核人选择“继续整改/拆分新问题/风险豁免” |
| inconclusive | 创建补测待办，不允许关闭 |

## 10.4 跨报告问题演进

### P1 当前可做的最小版本

- 同一 `Issue` 可在多个任务/报告中创建多个 `IssueOccurrence`。
- 用户在创建问题时可搜索并手动关联既有问题。
- 问题详情按时间显示所有出现、整改、复测。
- 报告中展示该问题“首次发现、最近状态、是否复现、关联报告数”。

### RESERVED：自动相似问题推荐

- 输入：产品/型号、模块、功能节点、标签、文本、图像/媒体特征（如后续启用）。
- 输出：候选问题及相似原因，不直接合并。
- 人工确认后创建 `issue_relation`，关系可为 `same_issue`、`related_issue`、`duplicate`、`split_from`。
- 必须保存模型/规则版本、候选分数、用户决策和误判反馈。
- 无论置信度多高，不得自动关闭、合并或改变历史问题。

# 11. 模块五：报告生成、阅读、审核、发布与导出

## 11.1 核心阅读与交互原则

1. 全量报告固定主线为：**报告信息 -> 报告总结 -> 问题点列表 -> 动态结果区 -> 行动与追溯**。
2. “报告总结”是唯一报告级叙事结论；顶部仅展示范围、状态、版本和关键计数，不重复结论文字。
3. 数据和证据不独立成模式；它们跟随问题、功能效果、指标异常、整改或复测出现。
4. 不向创建者暴露模板选择。系统根据业务类型和记录数据推荐 `render_profile`，审核人可在允许范围内确认布局。
5. 问题优先不等于“只看问题”：问题列表之后的动态结果区必须能解释问题产生的功能、食谱、指标、对象、证据和条件。
6. 无右侧抽屉。复杂信息采用当前行/卡片下展开、全屏媒体预览、独立问题详情页、独立指标明细页。
7. 工程深度查看不是独立 View Mode：在指标/矩阵上下文中提供筛选、冻结上下文、原始数据、公式和批量导出。

## 11.2 全量报告页面结构

```text
报告信息条
  标题 | 业务类型 | 产品/阶段 | 来源 | 状态 | 版本 | 问题计数 | 导出/分享
-----------------------------------------------------------------------
报告总结（唯一结论模块）
  总结正文 | 关键风险 | 下一步建议 | 人工确认 | 范围与可比性声明
-----------------------------------------------------------------------
问题点列表（默认优先）
  筛选：全部 / 未关闭 / A-B级 / 我的责任 / 待复测 / 已豁免
  行内：现象、影响、严重度、状态、关键证据、责任、计划、复测
-----------------------------------------------------------------------
动态结果区（按实际数据生成）
  功能/食谱效果 | 指标结果 | 对比矩阵 | 五感/操作 | 阶段演进 | 来源对齐
-----------------------------------------------------------------------
行动与追溯
  下一步任务/复测 | 来源任务/附件 | 快照/导出 | 版本/审计
```

## 11.3 报告信息条与报告总结

### 报告信息条

| 字段 | 规则 |
|---|---|
| 报告标题 | 规则生成，可由有权用户编辑；保留标题变更审计 |
| 业务类型 | `report_scope_type`；由来源/合并关系决定，不由布局代替 |
| 报告状态 | 草稿、审核中、已发布、失效、归档 |
| 产品/型号/阶段 | 可定位业务对象；阶段为服务端字典 code |
| 来源任务/报告 | 多来源显示数量，进入独立来源追溯页 |
| 可比性 | comparison/synthesis 必显；弱可比和不可比禁止默认排名 |
| 关键问题计数 | A/B、未关闭、待复测、已豁免；自动计算 |
| 版本 | 指向已发布快照版本，草稿显示工作版本 |
| 主操作 | 提交审核、发布、导出、分享；按权限与状态显示 |

### 报告总结

| 字段 | 规则 |
|---|---|
| 总结正文 | 建议 80-300 字；人工填写或确认 AI 草案 |
| 结论等级 | `positive / neutral / risk / blocked` |
| 关键风险 | 最多 3 条并列；更多风险在问题/动态区呈现 |
| 下一步建议 | 可关联任务、问题、复测或自由文本行动项 |
| 结论来源 | `manual / ai_confirmed / imported_draft`；历史兼容见 §14.4 |
| 确认人/时间 | 发布前必须有；AI 不能代替确认人 |
| 范围/可比性声明 | comparison/synthesis 必填；说明样本范围、条件差异、缺失项与限制 |

## 11.4 就地证据位、指标公式与数据契约

V2.6 的呈现能力在 V3.1 以“组件契约”保留，而不是以独立模式或抽屉保留。

| 能力 | V3.1 呈现方式 | 规则 |
|---|---|---|
| Evidence Slot | 行内 `evidence_strip` / 证据位 | 每个业务对象定义 `primary/supporting/archive/before_after` 角色；正文默认 1-3 个关键证据 |
| Metric Formula Panel | 指标行内展开或独立指标明细页 | 展示公式、阈值、原始值、单位、公式版本、计算者、异常说明与关联证据 |
| 固定上下文 | 矩阵/指标表的 sticky 项目列与对象头 | 超宽表分组或独立指标明细页；不能靠缩小字号解决 |
| 可比性声明 | 报告总结与比较区顶部 | 未确认可比性时隐藏排名/推荐，只显示差异与限制 |
| 快照 | 已发布不可变快照 | 阅读、分享和导出默认引用快照，不引用实时草稿 |

### 证据位规则

| 业务对象 | 推荐 `slot_role` | 正文展示规则 |
|---|---|---|
| 问题出现记录 | `primary` | 高等级问题至少 1 个可用证据或有豁免理由 |
| 食谱/功能效果 | `primary` / `supporting` | 卡片展示关键证据；步骤证据展开后可见 |
| 指标异常 | `primary` | 异常旁展示关联证据或明确“无可视证据”原因 |
| 整改/复测 | `before_after` | 支持整改前后对照；关闭问题必须有复测证据或获批准的豁免 |
| 报告总结/来源 | `archive` / `source_report_ref` | 用于追溯，不占正文主阅读空间 |

## 11.5 动态结果区与渲染策略

### 默认策略推断

| `render_profile` | 典型触发 | 默认展示重点 |
|---|---|---|
| `single_narrative` | 单对象、多记录项 | 功能效果 + 问题 + 就地证据 |
| `comparison_matrix` | 多对象且记录项可对齐 | 对象列 x 项目行、固定上下文、行级结论 |
| `metric_emphasis` | 多指标、阈值/公式重要 | 指标定义、异常解释、指标明细入口 |
| `mixed_comparison` | 图片、指标和问题同等重要 | 关键图 + 核心指标 + 问题标签 + 小结 |
| `stage_timeline` | 同型号跨阶段/复测 | 阶段轴、问题复现与关闭、效果演进 |
| `synthesis` | 多来源专题归集 | 来源范围、字段对齐、共性/差异/缺口 |

推断输入：`report_scope_type`、对象数、记录项对齐率、指标密度、阶段数、来源任务/报告数、可比性状态。无法安全推断时，回退 `single_narrative`，并在审核清单要求确认。

### 11.5.1 问题点列表

默认排序：未关闭 A -> 未关闭 B -> 待复测 -> 其他未关闭 -> 已关闭/豁免。

```text
严重度 | 现象摘要 | 影响 | 关键证据 1-3 | 当前状态 | 责任人 | 计划 | 复测结论
```

- 点击行：在当前行下方展开完整描述、出现记录、整改摘要、复测摘要、关联记录项与“进入问题详情”。
- 点击图片：全屏预览并支持前后对照；关闭后回到原行位置。
- 点击整改/复测：进入对应独立详情页或带焦点的任务页。
- 无关键证据：显示“证据缺失”与原因；不得以空白代替。

### 11.5.2 功能/食谱效果

默认卡片：

```text
名称 | 食材清单/前置条件 | 功能效果 | 一句说明 | 关键证据 | 关联问题
> 展开步骤与完整过程
```

- 步骤默认折叠；异常步骤、失败步骤和有证据/问题的步骤优先露出。
- 结果为“不达标”时，录入端自动打开问题创建区并预填上下文；不自动创建正式 Issue。
- 卡片内可跳转到关联指标、问题详情、复测任务；不通过独立“证据模式”寻找资料。

### 11.5.3 指标结果与指标明细页

- 报告正文默认显示核心指标、异常指标、缺失项和可比性状态。
- 指标值可行内展开公式、原始值、阈值、版本、录入来源、异常说明、关联证据/问题。
- “查看全部指标”进入**独立指标明细页**，保留报告/任务上下文、筛选条件与返回位置；支持仅看异常、仅看缺失、按对象/食材/指标筛选、下载当前表格。
- 不使用右侧抽屉；不恢复独立数据模式。

### 11.5.4 对比矩阵

- 固定项目列与对象头；对象超过 5 个时提示缩小范围、按组浏览或进入指标明细页。
- 单元格仅显示最小决策信息：关键图 1-2 张、核心指标、问题标签、简短结论。
- 点击单元格在当前矩阵下方展开完整记录和证据；复杂编辑进入独立详情页。
- 支持“仅看差异、仅看异常、仅看未关闭问题”；缺失项明确显示 `未测试/缺失/不适用`。

### 11.5.5 阶段演进与专题来源对齐

- `model_dossier_report` 使用阶段演进，展示阶段结论、问题新增/复现/关闭、关键证据、来源任务/报告；不生成最优阶段排名。
- `synthesis_report` 在专题结论前强制展示来源报告、字段对齐、冲突/缺失项与可比性边界。
- 问题演进通过 `Issue -> IssueOccurrence -> RectificationAction -> Verification` 轨迹呈现；初期仅支持人工关联。

## 11.6 审核、发布与导出前检查

### 审核清单

| 检查项 | 阻断/预警 | 规则 |
|---|---|---|
| 报告总结已确认 | 阻断 | 必须有有权人员确认 |
| 高等级问题证据 | 阻断 | 缺失需有批准豁免理由 |
| 不达标结果问题闭环 | 阻断 | 必须存在 IssueOccurrence 或批准豁免 |
| 指标异常解释 | 阻断 | 必须有异常说明或不适用依据 |
| 对比可比性 | 阻断 | comparison/synthesis 必须确认范围和边界 |
| 来源可追溯 | 阻断 | 至少关联来源任务/来源报告 |
| 导出快照可用 | 阻断 | 必须已发布或具备受控草稿导出权限 |
| 待观察/逾期整改 | 预警 | 允许发布但突出显示 |
| 正文证据过多 | 预警 | 不阻断，建议收敛到关键证据 |

### 发布与失效

- 发布创建不可变 `ReportSnapshot`，写入数据范围、引用对象版本、报告总结版本、渲染策略版本和可比性确认版本。
- 已发布报告允许生成新草稿，不直接覆盖已发布快照。
- 发现重大错误可 `invalidated`，必须填写原因；旧链接显示失效标识并提供最新有效快照链接（如有）。
- 发布后创建通知、搜索索引任务和可导出快照；导出不应阻塞发布事务。

## 11.7 最小 PDF Export Job（P0）

### 产品行为

- 用户只能导出自己有权查看的**已发布快照**；受控草稿导出仅对 reviewer/admin 开放且必须带水印。
- 点击“导出 PDF”后创建作业，不同步长时间等待；页面显示状态、最近一次产物、失败原因与重试按钮。
- PDF 内容与对应快照可见内容一致；视频以缩略图、标题、时间和受控链接/引用表示。
- P0 只支持统一 A4 标准导出；复杂 A3 矩阵、分册、分页预检、定制 Profile 为 RESERVED。

### 作业状态机

```text
queued -> preparing -> rendering -> uploading -> succeeded
                         |              |
                         v              v
                       retryable_failed  permanent_failed
                         |
                         v
                      retrying -> preparing
```

| 状态 | 用户可见文案 | 系统动作 |
|---|---|---|
| `queued` | 已加入导出队列 | 记录快照、权限、请求人、导出版本 |
| `preparing` | 正在准备数据 | 校验快照完整性、生成渲染 DTO |
| `rendering` | 正在生成 PDF | 渲染服务处理；写进度与 Trace ID |
| `uploading` | 正在保存文件 | 上传对象存储、生成受控下载链接 |
| `succeeded` | PDF 已生成 | 保存产物、校验 checksum、通知请求人 |
| `retryable_failed` | 生成失败，可重试 | 保留错误摘要、指数退避或人工重试 |
| `permanent_failed` | 生成失败，需要处理 | 创建管理员待办，禁止无限重试 |

作业必须记录：`snapshot_id`、`requester_id`、`template_version`、`renderer_version`、`attempt_count`、`trace_id`、`error_code`、`error_detail_sanitized`、`artifact_evidence_id`、过期时间。


# 12. 模块六：报告中心、搜索、分享与汇报简报

## 12.1 报告中心：列表、运营概览与 Action Inbox 边界

报告中心不替代全平台工作台。工作台聚合“我需要做什么”；报告中心聚焦“报告资产健康度、交付状态和风险”。

### P0：报告列表与轻量运营概览

| 区域 | 内容 | 行为 |
|---|---|---|
| 运营概览 | 待审核、发布阻断、已发布、已失效、含未关闭高优问题、导出失败 | 点击卡片带筛选进入列表；不展示与工作台重复的个人待办 |
| 报告列表 | 标题、产品/型号/阶段、业务类型、状态/版本、关键问题、来源、审核人、更新时间、分享/导出状态 | 兼容筛选、排序、分页、权限过滤 |
| 报告资产操作 | 提交审核、查看阻断项、查看导出作业、失效说明、分享状态 | 按状态/权限显示；所有操作可审计 |

筛选：产品线、品类、型号、阶段、状态、`report_scope_type`、`render_profile`、创建人、审核人、时间、可比性、是否含未关闭高等级问题、是否有导出失败。

### P1：报告 Action Inbox 与聚合视图

- 报告级行动项：待确认报告总结、待确认可比性、待补证据、待处理导出失败、待更新失效报告。
- 以报告为主体聚合，而不是复制任务/问题中心待办。
- 支持按产品线、阶段、审核人、发布状态、风险等级查看资产健康度。

## 12.2 全局搜索

- P0：任务编号、问题编号、报告编号、标题、产品型号的权限过滤搜索。
- P1：全文高亮、记录项/问题正文、证据说明、组合筛选、最近访问。
- 不在 P0 引入独立搜索引擎；阈值触发后再评估。

## 12.3 分享与外部阅读

- 默认不公开分享；创建链接需要 `share_report` 权限。
- 分享页只读取已发布快照，可设置密码、有效期、下载权限、水印。
- 分享页关闭编辑、整改、原始附件下载；视频播放/下载按组织策略控制。
- 链接撤销/到期返回 410，不展示缓存内容；访问、下载、导出均审计。

## 12.4 汇报简报翻页模式（Wave 2/P1）

简报是同一已发布快照的“决策阅读布局”，不是另一份需要手工维护的报告。

```text
Page 1  报告结论与范围/可比性声明
Page 2  关键问题与风险
Page 3  关键功能/食谱效果或关键矩阵
Page 4  关键指标/对象差异（有数据时）
Page 5  整改、复测与下一步
```

规则：

- 由快照数据自动生成，报告负责人仅能控制“是否纳入某关键问题/图表”，不能修改事实。
- 每页可跳转到全量报告对应章节；全量报告与简报共享 `snapshot_id`。
- 不代替工程师的完整矩阵、问题详情或指标明细页。
- P1 先支持浏览与投屏；基于 `ExportJob` 的简报导出在复杂 PDF Profile 立项后实施。

# 14. 模块八：AI 辅助、治理与字段兼容

## 14.1 P0 可启用的 AI 辅助

AI 仅作为草案、提示或辅助分析，不得直接改变业务事实、状态、责任人或发布结论。

| 能力 | 输入 | 输出 | 人工控制 |
|---|---|---|---|
| 报告总结草案 | 已授权的记录、问题、指标与证据说明 | `ReportSummary` 草案 | reviewer/owner 必须确认 |
| 缺失项提示 | 结构化完整性规则 | 缺证据、缺异常解释、缺可比性提示 | 用户修正或说明豁免 |
| 问题描述辅助 | 当前记录项、指标与证据说明 | 结构化问题草稿 | 用户编辑后才创建 Issue |
| 差异摘要 | 已确认可比的对象/指标 | 差异候选 | 不自动排名或推荐最优 |

## 14.2 禁止行为

- 不自动创建、关闭、合并或拆分 Issue。
- 不替换已人工确认的报告总结。
- 不在弱可比/不可比数据中输出默认最优推荐。
- 不把用户无权访问的任务、报告、证据送入模型上下文。
- 不将原始证据或个人信息以未批准方式外发。

## 14.3 AI 运行审计

每次 AI 调用创建 `ai_runs` 记录：`id`、能力类型、输入范围引用、模型/提示词版本、调用者、输出摘要、置信/安全标记、人工确认人/时间、拒绝理由、trace_id。模型输入保存为脱敏引用或批准的快照，不复制不必要的原始文件。

## 14.4 AI 字段重命名、回填与兼容期（Wave 0/P0）

现有实现可能包含 `ai_result`、`ai_summary`、`effect_ai_result` 等不同命名。V3.1 统一以 `ai_runs` + 业务对象引用 + `report_summaries.ai_run_id` 为权威模型，但必须分阶段迁移，禁止直接删除旧字段。

| 阶段 | 读写规则 | 数据动作 | 退出门槛 |
|---|---|---|---|
| M0 盘点 | 旧字段只读 | 统计非空率、来源、格式、引用路径 | 完成字段字典与消费者清单 |
| M1 回填 | 新旧双读 | 将旧值回填为 `ai_runs` 与关联引用；记录迁移批次/错误 | 抽样与总量校验通过 |
| M2 兼容 | 新字段单写、旧字段只读回退 | API 同时返回 `ai` 统一对象和 `legacy_ai`（受 Feature Flag 控制） | 所有前端/任务/导出消费者改用新 DTO |
| M3 冻结 | 旧字段不再写入 | 监控旧字段读取，告警并修复调用方 | 连续两个发布周期无旧字段业务读取 |
| M4 退役 | 旧字段移除或归档 | 保留迁移审计与必要备份 | 数据负责人、产品、研发共同批准 |

兼容 API 规则：

```json
{
  "summary": {
    "content": "...",
    "source_type": "ai_confirmed",
    "ai_run_id": "air_123"
  },
  "legacy_ai": {
    "available": true,
    "deprecated": true,
    "sunset_after": "2026-12-31"
  }
}
```

`legacy_ai` 仅用于兼容期，不得作为任何新功能的输入依赖。


# 15. Excel 来源附件、受控导入与质量校验

## 15.1 分阶段策略

| 阶段 | 能力 | 范围 | 约束 |
|---|---|---|---|
| Wave 1/P0 | 来源附件 | 上传并关联 Excel，作为证据/来源链接 | 不解析、不自动生成正式报告 |

| `import_jobs` | id, file_evidence_id, template_id, status, quality_score, error_json, created_task_id, created_report_id, trace_id |
| `import_field_results` | job_id, source_cell/sheet, target_object, target_field, raw_value, mapped_value, status, warning_code |
| `import_media_links` | job_id, source_sheet, source_anchor, evidence_id, target_hint, confidence, status |

```text
uploaded -> fingerprinting -> template_matched -> parsing -> mapping -> validating
    -> needs_confirmation -> drafting -> completed
                             |              |
                             v              v
                       retryable_failed  rejected/permanent_failed
```

- 模板不匹配：进入 `needs_template_selection` 或失败，不猜测。
- 字段映射冲突/合并单元格语义不明：标记 `needs_confirmation`。
- 图片与行项目无法可靠对应：导入为未关联证据候选，不自动绑定问题/结果。
- 所有生成对象为草稿，保留原 Excel 的 `SourceLink`、Sheet/单元格坐标与映射版本。

## 15.3 导入质量与错误处理

质量分只用于提醒与审核，不用于证明事实正确：

```text
质量分 = 必填映射完整度 + 来源可追溯性 + 指标公式可解析度 + 图片关联确认度 - 错误扣分
```

| 情况 | 系统动作 | 用户路径 |
|---|---|---|
| 模板版本未知 | 阻断导入 | 选择已支持模板或上传为来源附件 |
| 必填字段缺失 | 生成草稿但阻断提交 | 跳转到导入确认页的字段定位 |
| 指标公式不可解析 | 保留原文本、标记待确认 | 人工选择指标定义/填写原始值 |
| 图片锚点不可靠 | 不自动绑定 | 在确认页手动关联到记录项/问题 |
| 作业超时/服务异常 | 可重试失败 | 显示错误码、保留文件与已完成解析结果 |

## 15.4 RESERVED 高级导入

复杂图文、跨 Sheet 对齐、自由格式单元格、自动同问题识别、批量历史迁移，均需满足：冻结模板、黄金样本库、字段语义签字、人工确认界面、回滚/清理方案、性能预算和数据安全评审。


# 16. 数据模型、数据契约与数据库设计

## 16.1 技术选型建议

- 关系型数据库：PostgreSQL 15+；核心领域字段结构化，支持事务、JSONB、全文检索、分区、乐观锁。
- 文件存储：S3 兼容对象存储；媒体访问使用短期签名 URL；媒体元数据与业务对象关联分离。
- 异步任务：队列/消息系统（Redis Queue、RabbitMQ、Kafka 等按组织基线）；必须支持幂等、重试、死信与 Trace ID。

## 16.4 索引、约束与 JSONB 使用边界

- `tasks(task_no)`、`issues(issue_no)`、`reports(report_no)`、`export_jobs(id)` 唯一；`inbound_events(source_system, event_id)` 复合唯一。
- 所有写主表有 `version` 或等效并发控制；写接口要求 `If-Match` / `version`。
- 状态字段引用受控字典 code；合法跃迁由服务端状态机校验。
- `evidence_links` 对 `evidence_id,target_type,target_id,role` 建索引；禁止物理删除仍被快照引用的 Evidence。
- JSONB 可用于 `snapshot_json`、规则定义、输入范围、非固定扩展字段；不可替代可筛选的 status、owner、scope、version、关联 ID。
- 审计/事件表按时间分区或归档，避免主库膨胀。


# 17. API 设计与契约

## 17.1 通用约定

- 基础前缀：`/api/v1`；服务端以 OpenAPI/JSON Schema 输出权威 DTO。
- 用户写接口支持 `Idempotency-Key`；外部入站事件必须要求幂等键与签名。
- 并发更新使用 `If-Match` 或 `version`；冲突返回 `409 Conflict` 并返回可刷新范围。
- 返回包含 `trace_id`、`request_id`、`data`、`error`；所有列表均权限过滤与游标分页。
- 已发布快照、导出产物、迁移任务均有不可变引用；删除采用软删除/归档。
- `RESERVED` API 不注册生产路由或由 Feature Flag 显式拒绝，避免“文档有接口、实际被误用”。

## 18.2 Outbox、幂等与失败恢复

- 业务事务与 `outbox_events` 必须同事务落库；发布器至少一次投递，消费者以事件 ID + 聚合版本幂等处理。
- 任何异步任务（媒体、导出、迁移、导入、通知）必须有 `trace_id`、状态、尝试次数、错误分类与可恢复判断。
- 失败按指数退避重试；超过阈值进入死信队列并创建管理员或责任人待办。
- 异步结果不得覆盖人工后续编辑；以业务版本/更新时间决定是否生成待确认建议。
- 导出、迁移、导入的所有失败都可从对象详情页跳转到错误/恢复页面；错误信息需脱敏，内部堆栈只入日志。

## 18.3 前端技术路线

- TypeScript 严格类型；DTO/表单 schema 与服务端契约一致。
- 页面写操作均具备乐观更新与失败回滚；自动保存冲突显示“我的版本/服务器版本/合并建议”。
- 大报告使用虚拟列表、懒加载媒体；矩阵固定上下文但避免一次渲染所有高分辨率图。
- 深链必须携带 `focus`、`source`、`snapshot` 等参数，返回后保留筛选/滚动位置。
- 媒体直接上传对象存储，服务端完成签名、确认、扫描、转码和权限校验。
- 移动端优先录入；报告矩阵提供按对象分组的纵向卡片，不强制窄屏横向表格。
- 不实现右侧抽屉作为全局组件；局部展开、全屏预览、独立详情/明细页为标准交互。

## 18.4 后端模块边界

| 模块 | 责任 | 不应承担 |
|---|---|---|
| Identity/Permission | 认证、RBAC、资源范围、属性校验 | 业务状态计算 |
| Dictionary/Config | 字典、指标定义、Render Profile 配置 | 绕过状态机修改业务状态 |
| Task | 任务、分配、承接、状态 | 媒体转码、报告布局 |
| Record | 记录项、步骤、指标 | 问题关闭审批 |
| Media | 上传、扫描、转码、签名访问 | 报告语义推断 |
| Issue | 主档、出现、整改、复测 | 外部系统直写 |
| Report Aggregator | 报告投影、目录、动作项、快照、布局建议 | 编辑原始记录 |
| Export | Export Job、标准 PDF、产物、重试 | 发布审批 |
| Notification | 站内通知、渠道投递、升级 | 业务权限判定 |
| Migration | 回填、对账、回滚/补偿 | 线上正常写入 |
| Integration/Import | 未来接入、解析、映射、草稿创建 | 直接写核心表（必须调用领域 API） |

## 18.5 P0 标准 PDF 技术线路

```text
用户请求导出
  -> API 权限/快照校验
  -> 创建 export_jobs + outbox export.requested
  -> Export Worker 拉取快照 DTO
  -> 生成标准 A4 HTML/渲染内容块
  -> PDF renderer
  -> 对象存储 + checksum
  -> export.succeeded + 通知/审计
```

- 渲染输入只能来自已发布 `ReportSnapshot` + 对应 `report_print_blocks`，禁止直接读取实时草稿。
- Renderer 版本化；出现版式问题可定位到 snapshot、renderer 版本、print block 版本。
- 下载 URL 短时有效，下载权限在下载时二次校验。


# 19. 错误、失败、回退与恢复矩阵

| 模块 | 失败情形 | 用户看到什么 | 系统动作 | 恢复/回退 |
|---|---|---|---|---|
| 新建任务 | 必填字段缺失 | 字段级错误 + 顶部汇总 | 不创建任务 | 保留本地草稿 |
| 自动保存 | 网络中断/版本冲突 | “未同步/存在冲突” | 本地暂存、停止覆盖 | 重试；展示版本对比与人工合并 |
| 分配 | 人员无权限、离岗、范围不匹配 | 失败原因 + 可选承接组 | 不改变当前责任人 | 选择其他人/组；记录审计 |
| 媒体上传 | 文件超限、病毒扫描、转码失败 | 上传失败或“处理中失败” | Evidence 标记失败、保留元数据 | 更换文件/重试处理；未可用证据不可满足阻断条件 |
| 问题关闭 | 无复测证据或无审批权限 | 阻断项与“去补充”跳转 | 拒绝状态跃迁 | 补复测、申请豁免或由审核人处理 |
| 报告发布 | 质量清单不通过 | 阻断项列表、定位链接 | 不创建快照 | 修复后重新提交 |
| 导出 | renderer/存储/超时失败 | 导出作业状态、错误摘要、重试按钮 | 分类为可重试/永久失败；创建动作项 | 自动重试或人工重试；永久失败升级管理员 |
| AI 草案 | 模型超时、权限/安全拒绝 | “未生成草案”且不影响人工编辑 | 写 ai_run 失败状态 | 可重试；不回退已有人工总结 |
| 字典变更 | code 已被引用或影响状态规则 | 拒绝删除/改 code | 保留历史项、禁用新选项 | 新建替代项；迁移引用后再退役 |
| 数据迁移 | 校验不一致/批次失败 | 管理员迁移面板告警 | 停止后续批次、保留幂等标记 | 执行补偿/回滚脚本；不切换 Feature Flag |
| Excel 导入 | 模板不匹配/字段冲突 | 确认页或失败原因 | 不生成正式报告 | 选择模板、修正映射、保留来源附件 |
| 外部事件 | 签名不合法/重复/字段缺失 | 对业务用户无误导提示 | 拒绝、去重或进入死信 | 集成管理员修复映射后重放 |

错误代码需按域前缀命名，例如 `TASK_*`、`ISSUE_*`、`REPORT_*`、`EXPORT_*`、`MIGRATION_*`、`IMPORT_*`、`INTEGRATION_*`。所有错误必须有 `trace_id`。


# 20. 审计、安全、隐私与数据保留

## 20.1 审计范围

必须审计：

- 状态变化：任务、问题、整改、复测、报告。
- 责任人、严重度、计划日期、可比性、报告总结的修改。
- 证据上传、删除、替换、下载与外部分享访问。
- 发布、失效、分享、导出。
- 权限、分配规则、指标公式、导入模板、集成映射的配置变更。
- AI 生成、确认、拒绝和应用。
- 外部事件接收、重放、失败、回写。

审计日志至少包括：操作者、时间、对象、动作、前后值、IP/客户端（按合规策略）、Trace ID、来源系统/自动化标记。

## 20.2 安全要求

- 对象存储默认私有；前端通过短期签名 URL 访问。
- 外部共享内容使用快照，禁止透传草稿或原始权限范围外数据。
- 外部集成密钥保存在密钥管理服务，不写入数据库明文或日志。
- 入站 Webhook 校验签名、时间戳与事件 ID，限制重放。
- 上传文件进行病毒扫描和格式白名单校验。
- 报告导出与分享遵守数据权限，敏感字段可按配置脱敏。
- 生产环境日志不得记录访问令牌、完整签名 URL、敏感原始数据。

## 20.3 数据保留

- 已发布报告快照、问题闭环记录和关键证据遵从质量记录保留周期。
- 已取消任务和失败导入按组织策略保留，可在到期后清理。
- 审计日志单独归档，至少满足内部审计周期。
- 物理删除前必须校验是否被已发布快照、问题或导出引用。

# 24. 旧数据迁移、回填、兼容与回滚

## 24.1 迁移总原则

1. 先盘点、后映射、再回填；先影子校验、后双读、再单写；最后退役旧字段。
2. 迁移以可重入批次执行；每批写入 `migration_runs`、`migration_items` 与 trace_id。
3. 永不覆盖已发布快照；迁移后的新投影/新引用必须保留旧对象来源。
4. 不以“数据库迁移成功”作为完成标准；必须做总量、关键字段、抽样视觉、权限和业务路径验证。
5. Feature Flag 分环境、分组织、分数据批次启用；出现异常可回退读取旧字段/旧投影。

## 24.2 映射清单

| 旧实现/数据 | 新对象 | 映射规则 | 双写/回退 |
|---|---|---|---|
| `materials.owner_type/owner_id` | `evidences` + `evidence_links` | 原文件元数据进入 Evidence；每个 owner 关系进入独立 Link；不明 owner 进入待确认清单 | 新读优先，旧 owner 可回退读取至清零 |
| 单表 `issues` | `issues` + `issue_occurrences` | 旧问题生成主档；每条历史发现/报告/记录引用生成至少一个 Occurrence；无上下文生成“历史迁移出现记录” | 旧字段只读兼容；新操作只写新结构 |
| `issue_re_evaluations` | `verifications` + evidence links | 复评估结果映射为 Verification；关联原问题与证据 | 双读到验证链路稳定 |
| `reports.content.ai_summary` | `report_summaries` + `ai_runs` | 文本、来源、确认状态按字段字典回填；未知来源标记 `legacy_unknown` | 见 §14.4 |
| 报告内容 JSON | `report_view_configs` / outline / action items | 可提取关系字段结构化；原 JSON 保留在 snapshot/legacy payload | 新渲染优先；出现异常回退旧阅读 DTO |
| 旧状态文字 | 服务端字典 code | 建映射表；不能映射时进入 `legacy_unknown` 并阻断新状态流转 | 历史显示保留原文 |

## 24.4 回滚与补偿

- 回填新表为新增/可标记失效的记录；禁止对旧数据做不可逆删除。
- 迁移批次出错：关闭该批次 Flag、停止后续批次、标记批次失败、执行补偿脚本或隔离新记录。

## 27.2 A 类：业务与数据规则补丁

### 27.2.1 AI Provider 政策（Bear-Model-VL 默认）

主文 §14.1 保留不变，V3.1.1 增补以下硬约束：

- **默认 provider_code**：`bear_model_vl`
- **默认部署地址**：由环境变量 `AI_BEAR_VL_BASE_URL` 提供；当前部署环境默认值 `http://ds.bears.com.cn:8000/v1` 可写入部署说明文档，但禁止成为前端常量、数据库业务字段或硬编码业务逻辑
- **目标模型**：由环境变量 `AI_BEAR_VL_MODEL` 提供；当前目标 `Bear-Model-VL`；模型服务实际接受的模型 ID 必须经上线前契约测试确认，不能只依赖名称约定

- **上线前契约测试**：执行模型清单、健康检查、请求/响应契约、超时、重试、并发和脱敏测试，并归档测试结果

### 27.2.6 阶段聚合可执行规则（补强 §11.5 stage_timeline）

**一级分组**：按 `project_phase_dict.sort_order` 排序；禁止前端/后端 `PHASE_ORDER` 硬编码。

**二级分组**：阶段显示名 + `YY/MM/DD`。

**日期取值优先级**：

1. `stage_date`
2. `task.completed_at`
3. `record_item.observed_at`
4. `task.created_at`

**同一天多次任务**：阶段名 + `YY/MM/DD` + 任务号；若任务号不适合展示则补 `HH:mm`。

**无阶段回退**：按 `YY/MM/DD` 分组，不强行归入"试制/试产"等阶段。

**无阶段且无日期**：归入"日期未标注"段，置于时间线末尾；审核清单提示"阶段/日期缺失"。

**快照固化**：已发布快照必须固化当时的阶段名称与排序值，避免后续字典改名导致历史报告发生变化。

## 27.4 C 类：等保三级准备度矩阵（治理工作流并行）

V3.1.1 不直接承诺"系统已达到等保三级"。GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》为现行标准；是否需要达到三级、保护对象范围如何界定、是否需备案及测评，应由正式定级与合规评估决定。实际项目通常包含：定级 → 备案 → 建设整改 → 测评 → 监督检查。

PRD 增补"准备度矩阵"作为与 Wave 0 并行的治理工作流，不等同于已通过测评：

| # | 治理域 | 准备度要求 |
|---|---|---|
| 1 | 账户与身份认证 | 最小权限、角色与数据范围控制、多因子、会话治理 |
| 2 | 操作审计 | 管理员、用户、导出、分享、权限变更等关键操作可审计 |
| 3 | 数据分类分级与保护 | 重要数据分类分级、传输与存储加密、备份恢复 |
| 4 | 文件安全 | 上传文件扫描、恶意文件隔离、签名 URL 时效、下载二次鉴权 |
| 5 | 网络与边界 | 服务间认证、环境隔离、漏洞修复与入侵监测 |
| 6 | 可用性与容灾 | 高可用、容灾、日志留存（≥6 个月）、告警处置、应急预案 |

# 28. 结论

V3.1 的核心不是把 V2.6 的页面能力全部搬回，也不是把 V3.0 的领域模型无限扩张，而是形成一条可实施、可验证、可迁移的主线：

```text
接到任务
 -> 记录事实
 -> 发现并关联问题
 -> 留下可追溯证据
 -> 推动整改与复测
 -> 发布不可变报告快照
 -> 可靠导出与阅读
 -> 沉淀跨阶段问题历史
```

系统以 V3.0 的任务与问题闭环为业务骨架，以 V2.6 的证据、公式、矩阵、可比性和快照能力为呈现能力库，并用 V3.1 的数据契约、字典、兼容期、Export Job、迁移与 Wave 门禁解决落地风险。

当前实现优先级明确：先完成 Wave 0 技术地基，再实现 Wave 1 业务闭环；汇报简报、报告运营、跨报告追溯和受控 Excel 导入进入 Wave 2；外部集成、通用导入、智能关联、复杂 PDF 均保留完整设计但不提前进入开发。
