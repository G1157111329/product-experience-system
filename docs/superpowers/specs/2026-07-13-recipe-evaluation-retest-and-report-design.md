# 功能评价、整改复测与冻结报告收口设计

日期：2026-07-13
状态：已确认

## 目标

把功能/食谱的判断从“逐条问题点录入”收口为“对整个功能/食谱作合格、不合格、待定判断”，让问题同步、整改复测和冻结报告围绕同一判断工作。相同三态规则同时覆盖五感体验及其他已有结果判断的录入模块。

## 1. 录入交互

- 不改变点击体验计划后的默认落点。
- 功能/食谱效果区保留三段式单选、评价描述和效果素材；三段式为“合格 / 不合格 / 待定”，默认待定。
- 描述失焦自动保存；状态点击立即保存；素材选择和取消关联自动保存，并反馈保存中、已保存、保存失败。
- 删除效果问题点输入、“保存素材/问题点”按钮、独立 AI 总结/结果组件。
- AI 入口改为评价描述框内的小图标。AI 读取当前描述和素材，只生成综合评价文字并回填、自动保存，不替用户选择判断状态，不独立展示评分。
- 删除步骤问题点的新建、编辑和展示。旧字段暂不删列，历史冻结数据也不再渲染步骤问题点。

## 2. 问题同步规则

- “不合格”和“待定”均同步到问题管理；“合格”不新建问题。
- 功能/食谱问题标题分别为“〈用户命名〉食谱/功能效果不合格”和“〈用户命名〉食谱/功能效果待定”。其他录入模块沿用检查项名称并附判断结果。
- 同一任务、同一来源对象只维护一个问题，状态切换不得重复建项。
- 一旦问题已创建，不因原评价被修改或复测合格而删除；原始判断与整改结果分开保存。
- 五感体验及其他存在三态判断的录入模块采用同一规则，待定也进入冻结报告的问题 Tab。

## 3. 整改复测

- 功能/食谱原“问题点”位置改为整改复测区；任务详情与问题管理复用同一数据和交互。
- 每次正式复测包含三段式结果、评价描述、素材、录入时间和录入人；状态默认待定。
- 复测使用明确的“保存复测”动作，避免自动产生空历史。描述框同样提供内嵌 AI 图标，只回填文字。
- 最新复测为合格时，问题标记为整改完成；不合格时保持整改中；待定时回到待整改。问题始终保留。
- 默认突出最新记录，其余记录折叠为“查看全部 N 次复测”。
- 每条复测可二次确认后删除。删除时解除素材关联但不删除素材库文件，然后按剩余最新记录回算问题状态；无剩余记录时恢复原始不合格或待定状态。该过程必须原子化或具备等价的一致性保证。

## 4. 冻结报告问题版式

- 功能/食谱问题按整体判断进入问题列表，不再依赖效果问题点文本。
- 展开项依次包含：名称、配方/参数、步骤数量、原始效果评价、原始效果素材，以及整改完成时的整改效果评价和整改素材。
- 步骤为 0 时不显示步骤行；否则显示“食谱步骤：N步”，步骤明细默认折叠，展开后只显示步骤内容和证据素材，不显示步骤问题点。
- 只有 1 次复测时直接展示该次结果、描述和素材；复测不少于 2 次时正文只显示最新一次，并显示“整改复测记录数：N”。
- 原始名称、配方、参数、步骤、判断、评价和素材以 `snapshot_id` 对应快照为真源；报告生成后的问题状态、最新复测和整改素材作为实时整改信息叠加，不能改写冻结事实。
- 报告详情、匿名分享、浏览器打印和服务端 PDF 共用同一投影与显示规则。

## 5. 数据与兼容

- 统一服务层状态为 `qualified / unqualified / pending`，UI 显示对应中文。
- 问题权威状态仅保留 `open / rectifying / verified_closed / waived`，UI 分别显示“待整改 / 整改中 / 整改完成 / 不整改”。旧 `triaged / assigned` 迁移为待整改，旧 `pending_verification / reopened` 迁移为整改中；不再提供“已重开”状态。
- 功能/食谱沿用 `recipes.effect_status`；复测记录新增独立结果字段；既有检查记录通过规范化映射接入统一问题同步。
- 新增迁移须同步 Drizzle schema、`database-schema.sql` 和迁移登记。新环境依次执行 0013、0014、0015 后再执行本次迁移。
- 旧效果问题点和步骤问题点字段保留为兼容数据，不再写入、不再参与新问题生成、不再展示。
