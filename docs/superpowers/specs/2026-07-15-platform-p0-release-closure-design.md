# 平台 P0 发布阻断收口设计

日期：2026-07-15

状态：方案 A 已确认，等待书面规格复核

范围：当前工作树中的在途实现、权限与外部入口、删除与状态事务、素材多目标关联、冻结报告问题真源、保存与提交门禁、破坏性操作、移动端矩阵阅读、数据库与部署门禁

## 1. 目标

本轮以当前工作树的 256 项修改与新增内容作为受保护的在途基线，不回退、不覆盖、不重新实现已经落地的功能。在现有 2026-07-11 至 2026-07-15 设计与实施计划之上，完成三角色审计确认的发布阻断项，并在所有开发队列清空后只执行一次本地 Docker 全局部署与逐项验收。

最终发布结论只有两种：

- `PASS`：代码门禁、数据库门禁、Docker 健康、真实浏览器主链路和故障注入全部通过。
- `BLOCKED`：任一 P0 验收项没有可复现通过证据，或受外部条件阻断。

不得以类型检查通过、单个 API 成功或局部页面可见代替全局验收。

## 2. 受保护基线

### 2.1 工作树保护

- 当前未提交内容视为用户在途成果，只允许增量修复。
- 每个任务包必须声明独占主文件和可修改 allowlist。
- 不执行 `git reset --hard`、`git checkout --`、全仓格式化或批量覆盖。
- 不暂存无关文件；每个规格或代码提交只暂存明确 allowlist。
- `tmp/deploy-report-runtime/.next` 等生成物不是产品代码，最终 lint 前从扫描范围排除或清理，但不得借此删除用户业务文件。

### 2.2 不得回归的产品合同

- 任务顶部状态卡是唯一任务内模块导航，不恢复第二套录入目录。
- 不恢复独立“问题输出—确认”步骤；问题由服务端同步进入问题管理。
- 任务底部是唯一素材证据区，数据矩阵不恢复素材池。
- 新数据矩阵最多两级层级；历史三级数据仅兼容读取。
- 空矩阵不显示“已创建”，最新空矩阵不能遮蔽更早有效矩阵。
- 报告详情、匿名分享、浏览器打印和服务端 PDF 读取同一冻结事实源。
- 问题状态只显示一次。依据 `AGENTS.md` 2026-07-15 最新规则，右侧直接显示四态文案；有权限时点击状态进入整改，不额外显示“查看整改”。
- 报告素材原位呈现，不新增附录 Tab，不把匿名分享改为登录后访问。

### 2.3 明确排除的高风险迁移

以下项目不纳入本轮，不得在修复 P0 时顺手实施：

- VARCHAR 主键与外键迁移为 PostgreSQL UUID。
- `check_records` 宽表范式化。
- AI 配置密钥版本、轮换和重加密。
- 任务、问题、标准列表改为游标分页及复合索引迁移。
- `issues.severity/priority/level` 字段合并。

## 3. P0 工作包

### 3.1 P0-A：权限与外部入口

#### 范围

- 企微回调必须校验签名、时间戳、nonce、CorpId 和 AES 消息；缺少密钥或配置时 fail closed。
- 回调必须防重放，重复 msgId/nonce 不得再次产生素材任务。
- Agent 建议块决策必须从 block 反查 run、conversation、user 和目标资源归属，不接受客户端替换目标矩阵。
- 矩阵 AI 总结在调用模型和创建 run 前必须完成资源级授权。
- 普通用户待归属素材池只返回自己上传或自己有权访问的素材；管理员全局视图必须显式区分。

#### 验收

- 无效签名、重放、CorpId 不匹配的企微请求均被拒绝且不入队。
- 双用户 IDOR 测试证明 suggestion block、matrix summary、unassigned materials 互不可见、不可写。
- 所有拒绝路径不调用模型、不创建 run、不新增业务数据，并写安全审计日志。

### 3.2 P0-B：删除、状态与整改事务

#### 范围

- 问题状态变更、整改动作创建与审计写入属于一个事务。
- 检查记录删除、食谱步骤删除、食谱删除及对应素材解绑属于一个事务。
- 客户端不再逐条预删食谱步骤后再删除食谱；删除由服务端单一事务入口完成。
- 失败时不得留下“整改中但无整改动作”、记录仍在但证据丢失、食谱半删除等状态。

#### 验收

- 对每个写步骤执行故障注入，任一步失败均完整回滚。
- 成功删除只解除当前目标关联，不物理删除仍被其他目标或冻结报告引用的资产。
- 重复请求具有明确幂等结果，不产生重复整改动作或重复清理。

### 3.3 P0-C：素材多目标关联与冻结媒体保护

#### 范围

- `material_links`、legacy FK 兼容字段及素材派生状态在一个事务中更新。
- 改绑必须先建立新关联，确认成功后再解除旧关联；失败保持原关联。
- 普通业务位置的“移除素材”只删除当前位置 link。
- 资产级物理删除必须验证无活动 link、无冻结报告引用且调用者拥有资产级权限。
- 冻结报告媒体采用引用保护或不可变冻结副本。实施计划必须选择一种方案并提供迁移与回滚说明。

#### 设计选择

本轮默认采用“冻结引用保护”：快照记录稳定素材身份和存储 key，存在冻结引用时禁止物理删除文件。它对当前 Garage/local 双路径改动最小，也不会复制大量视频。未来如需法规级不可变归档，可独立升级为冻结副本。

#### 验收

- 同一素材绑定三个目标后解除一个，另两个继续可见。
- 改绑第二步失败时旧关联仍存在。
- 删除活动素材后，已发布报告详情、匿名分享、打印和 PDF 仍可读取原媒体。

### 3.4 P0-D：冻结问题真源与复测历史

#### 范围

- 冻结问题与 live issue 只按稳定身份关联：linked issue id、issue-point/cell id、record id、recipe id、comparison cell 和问题索引。
- 删除标题匹配回退。同名不同来源问题必须分别保留。
- 报告阅读页不得因缺少 live issue 临时创建 canonical issue；缺失关联显示可理解的完整性状态。
- Frozen ViewModel 保留有序复测历史，不在服务层永久裁成 `count + latest`。
- 默认显示最新复测；两次及以上提供可键盘展开的历史入口。打印/PDF连续呈现完整历史摘要。
- 右侧整改状态在详情和匿名分享始终存在，只显示一次；有权限时可点击。

#### 验收

- 同名不同矩阵/记录/食谱的问题不串状态、不误合并。
- 打开报告前后 canonical issue 数量不变化。
- 0、1、2 次及以上复测均按合同显示，历史素材归属正确。
- 详情、分享、打印和 PDF 的问题数、身份、状态与复测内容一致。

### 3.5 P0-E：保存、离开与报告生成门禁

#### 范围

- 报告生成、模块切换和离开任务前使用可传播失败的统一 flush。
- 不使用 `Promise.allSettled` 吞掉保存失败后继续生成报告。
- 保存失败保留本地草稿、显示具体字段或记录、提供重试，并阻断报告生成。
- 页面卸载的 fire-and-forget 保存不能作为唯一保障；存在脏字段时阻止路由离开或给出明确放弃确认。

#### 验收

- 注入一个自动保存 500 后，生成报告请求数为 0。
- 延迟保存期间触发后退、侧栏导航和关闭页面，系统阻止离开或明确确认放弃。
- 重试成功后可继续生成，冻结快照包含最后一次输入。

### 3.6 P0-F：破坏性操作反馈

#### 范围

- 删除五感记录、对比矩阵大类/细项、食谱和步骤前必须显示真实影响范围。
- 确认内容至少包含受影响记录、子节点、单元格、素材关联和问题关联数量。
- 取消时不发送删除请求；失败时保留界面和数据，不显示成功 Toast。
- 修正五感记录删除成功文案，不得继续显示“问题点已删除”。

#### 验收

- 取消、服务端失败和成功三条路径均有浏览器断言。
- 大类级联删除的影响数量来自服务端权威投影，而不是前端猜测。

### 3.7 P0-G：移动端矩阵阅读与可访问性

#### 范围

- 390px 冻结对比矩阵不得依赖横向滚动作为主阅读路径；采用按项目或对象分段的静态布局。
- 真实 8 至 15 列数据矩阵在窄屏采用字段分段或静态分页，避免把全部列压入单行。
- 桌面冻结矩阵继续遵循最新紧凑横向表格规则；移动阅读分支不得改变冻结事实与打印列序。
- 移动数据矩阵上一行/下一行点击区域不小于 44×44px。
- 食谱和步骤排序提供键盘进入、上移、下移和位置播报。

#### 验收

- 390、768、1024、1440 四种宽度无非必要页面级横向滚动、文字覆盖或不可读列。
- 12 列、长中文、视频 poster、问题点的真实样本通过移动浏览器检查。
- 键盘可完成排序并在刷新后保持权威顺序。

### 3.8 P0-H：数据库能力与启动门禁

#### 范围

- 本轮生产支持合同收口为 `self-hosted-postgres`。这是当前生产实际运行模式，也是本轮必须完整验收的数据库路径。
- `supabase-service-role` 保留代码与未来兼容目标，但在核心报告、矩阵、Agent 和分析能力达到等价前明确标记为实验性禁用；生产启动选择该模式时必须 fail closed，并说明当前不受支持，不能继续以“双模式已可生产使用”对外描述。
- 启动探针增加应用 schema manifest：核心表、列、FK、约束、索引和 migration journal tag。
- `SECURITY_SCHEMA_VERIFIED=true` 只是前置声明，不能替代真实数据库探针。

#### 验收

- 分别移除一个核心表、列、FK 和 journal tag，应用必须拒绝启动并输出缺失迁移标识。
- 完整 self-hosted PostgreSQL 数据库正常启动，矩阵、报告、Agent、问题、素材核心 API 不出现 schema 500。
- 文档、环境变量校验和启动错误必须一致声明 Supabase service-role 当前为实验性禁用；不得在这一轮删除相关兼容代码或迁移数据。

## 4. 执行与智能体分工

采用串行集成、分域实现：

1. 产品经理审查每个任务包是否符合最新 PRD、AGENTS 和已确认非回归边界。
2. 实现智能体按独占文件边界执行 RED → GREEN → REFACTOR，并完成自检。
3. 规格审查智能体只判断是否满足本设计和现行 PRD，不做顺手扩展。
4. 代码质量审查智能体检查权限、事务、兼容、错误处理、性能和可维护性。
5. 主责检查 diff、解决跨包冲突并运行定向门禁。

多个实现智能体不得同时编辑共享的材料服务、报告冻结模型、任务详情页或数据库 schema。只读审计可以并行，代码集成必须按依赖顺序串行：P0-A → P0-B/C → P0-D/E → P0-F/G → P0-H。

## 5. 验证策略

### 5.1 开发期间

- 每个问题先建立可见 RED，再实现 GREEN。
- 只运行当前工作包的单元、契约、故障注入或集成测试。
- 不在每个问题后重建 Docker，不反复重置数据库。
- 通过 `pnpm ts-check`、相关定向测试和 scoped lint 判断是否可以进入下一包。

### 5.2 队列清空门禁

在启动 Docker 前必须同时满足：

- 所有 P0 工作包规格审查和代码质量审查通过。
- 所有定向测试通过，失败数为 0。
- `pnpm ts-check` 通过。
- `pnpm lint` 通过；生成目录不得污染 lint。
- `git diff --check` 通过。
- `pnpm build` 通过。
- 数据库迁移 journal、schema、`database-schema.sql` 与探针合同一致。

### 5.3 唯一一次本地 Docker 部署

队列清空后执行：

```bash
docker compose -f docker-compose.local.yml up -d --build
docker compose -f docker-compose.local.yml ps
```

Docker 验收期间不再插入新的设计范围；发现回归时记录为 `BLOCKED`，修复后允许重建同一最终验收环境，但不得把未通过结果包装为 PASS。

### 5.4 全局回放矩阵

- 权限：双用户、管理员、匿名分享、无签名企微回调、越权 Agent 请求。
- 数据完整性：删除和绑定每个阶段的故障注入、事务回滚、重复请求。
- 任务录入：自动保存失败、页面离开、报告生成门禁、移动连续录入。
- 问题闭环：四来源问题、同名不同身份、整改动作、0/1/多次复测。
- 素材：一个素材多目标复用、解除一个目标、冻结后删除、local/S3 fallback、视频 poster。
- 报告：详情、匿名分享、浏览器打印、服务端 PDF 的问题数、矩阵、素材和状态一致。
- 响应式：390、768、1024、1440 宽度；对比矩阵与 12 列数据矩阵真实样本。
- 运行时：应用与 PostgreSQL healthy、启动日志、核心 API 无 500、浏览器控制台无新增错误。
- PDF：HTTP 200、`application/pdf`、文件头 `%PDF`，横向矩阵没有裁切或丢失表头。

## 6. 完成定义

本轮只有在以下条件全部满足时才能声明完成：

- 三角色审计中的 30 个候选均映射到已完成、已合并重复项、降级并说明理由，或明确 BLOCKED。
- 八个 P0 工作包均有代码、测试和验收证据。
- 当前工作树原有在途成果未被回退或覆盖。
- 所有代码门禁通过。
- 唯一一次集中 Docker 验收完成。
- 每项验收均记录 PASS/BLOCKED、命令、可观察结果和相关证据路径。
